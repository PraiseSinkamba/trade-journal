# Phase 16 — Persistent workflow command/transition engine

Phase report for the Phase 16 subset of the AI-native journal run (milestone M5, task packet
T-016): the **workflow half** of detailed-plan Task 11. Binding scope: design §13 (workflow
contract), §15 (conversation and interaction contracts — tables only), contract review §§2–6; the
phase guide's Phase 16 row ("Task 11 workflows only", schema allocation `0007`).

## Outcome

A workflow is a durable, versioned process that lives in the journal. It starts in `running`, hands
itself to the user when its effect runs, and ends when the user answers. Every applied transition
writes a row, advances the workflow's own revision and enqueues its durable effect **in the same
transaction** — so a crash can neither lose the effect nor apply it twice. A command that does not
apply changes nothing at all: a stale expected revision conflicts, the same command id with the
same payload replays the stored result, and the same command id with a different payload is a
conflict rather than a second application. A workflow that waits for the user holds no job, and
every transition releases the jobs of the state it leaves. A correction is a self-report: the
user's own words plus the evidence the workflow already carries, written to the workflow and to the
transition history, and never to a trade, a fill, an annotation, a hash or a key.

**Engagement is not in this phase.** The engagement tables exist because the phase guide allocates
them to migration `0007`; no engagement policy, cooldown, dismissal, expiry or opportunity behaviour
exists. That is Phase 17.

Notes on the constraints:

- `status` is checked against the six workflow statuses and `action` against the six recorded
  transition actions; the SQL check constraints and the Drizzle enums agree.
- `account_id` is explicit on every account-owned row and cascades from `accounts`, so an account
  purge removes every record that holds the deleted account's data. A null `account_id` is a shared
  (account-independent) row.
- The four Phase 17/18 tables (`intelligence_opportunities`, `intelligence_conversations`,
  `intelligence_messages`, `workflow_conversations`) are created here and used by nobody yet, as
  the phase guide's allocation requires ("Tables grouped within a migration may be created together
  when their FKs/constraints form one coherent schema").
- Migrations `0001`–`0006` are **byte-unchanged**; their checksums in `migration-checksums.json`
  are unchanged. The manifest was regenerated by `pnpm --filter web migrations:build`, never by
  hand, and `pnpm --filter web migrations:check` reports it up to date.

**Backup and rollback impact.** The migration is additive: it creates new tables and rewrites
nothing, so a legacy journal and a fresh journal converge on the same schema. A rollback is a
forward repair (a later migration dropping the new tables), never a destructive down migration. The
new tables hold no financial data, so a restore needs no special handling beyond the ordinary
journal backup.

## Deviations

1. **The store is an injected port, not an import.** The brief sketched the engine as reaching the
   adapter directly. The repository's own import-boundary rule (`rule 5` of
   `apps/web/tests/intelligence-boundaries.test.ts`) allows a domain to reach a sibling's
   `contracts/` and nothing else, and only `composition.ts` may wire a concrete adapter. The
   `ExperienceStore` port therefore lives in `contracts/experience.ts` and the SQLite adapter is
   injected into `createWorkflowEngine`. The boundary rule stays intact without an exemption. The
   plan was amended in the implementation commit to record this.
2. **One file outside the phase's own list was touched**:
   `apps/web/tests/intelligence-knowledge-revisions.test.ts`. The Phase 14 fixture "upgrades a
   journal that is at 0005" dropped the four `0006` tables and deleted the version 6 ledger row,
   which was the newest version then. With `0007` registered, that fixture leaves the ledger at
   `{1..5,7}`, which the runner correctly refuses ("Migration history is not contiguous"), and every
   later case in the suite then fails. The fixture now also drops the seven `0007` tables and the
   version 7 ledger row. The change is mechanical and weakens no expectation; the suite is 27/27
   green.
3. **The worker wiring is deferred.** `effectHandler()` exists and is tested, but registering it in
   `infrastructure/worker.ts` (`findHandler`) and in `composition.ts` is not this phase's work: the
   coordinator's file list for Phase 16 names neither file, and nothing composes the engine yet, so
   no `workflow_effect` job can be enqueued in production. A worker that met such a job without the
   registration would fail it terminally — which is why the registration is a prerequisite for the
   phase that composes workflows.
4. **A correction completes the workflow.** `correct` moves the workflow to `completed` and records
   the self-report; it does not re-enter `running` and it enqueues no job. The detailed plan's state
   path is `running → waiting_for_user → completed | cancelled`, and a re-evaluation of a corrected
   observation is not part of the workflow engine's contract. The recorded self-report is the
   handoff for the phase that consumes it.

## Next-phase handoff inputs

- **Phase 17 (engagement)** can now write `intelligence_opportunities`: the table exists with a
  unique `dedup_key`, an eligibility index, an expiry index and an explicit `account_id`. No
  engagement behaviour exists yet — `decideEngagement`, the central defaults, the 24-hour
  per-subject cooldown, the at-most-one-proactive-delivery-per-day rule, the dismissal and the
  seven-day expiry are all still to be built, against the tables this phase created.
- **Phase 18 (interaction routes)** needs a `POST` that returns a `WorkflowResult`: `409` for a
  stale revision, `400` for an invalid command, `401` unauthenticated, `403` for a denied scope or
  origin. The engine returns `{kind:"conflict", currentRevision}` for a stale revision and a
  conflict of scope or an illegal transition; an invalid command **throws** out of
  `workflowCommandSchema`, so the route must map the throw to `400`.
- **The worker registration** (`findHandler` for `workflow_effect`, plus the composition wiring)
  is a prerequisite for any phase that composes the engine and lets a worker run the effect jobs.
- **The conversations and messages tables** are created and empty: the join table keeps a workflow
  and a conversation independent, and a workflow may be linked to several conversations.
- The knowledge side of a correction is **not** implemented: a correction is a self-report on the
  workflow, not a `knowledge_sources` revision, so it does not invalidate dependent knowledge the
  way a note or a playbook correction does (Phase 14).
